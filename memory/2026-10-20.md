### 1. web_search 结果被外部化成 artifact(新踩法)

   应该直接 grep artifact 取事实。**

### 2. 本机死代理端口又变了: 7897 → 6696
cron prompt 里写死的是 `HTTP_PROXY=127.0.0.1:7897`, 今天的实际值是
`HTTP_PROXY=http://127.0.0.1:6696`(同样是死端口)。
→ **说明: 不要再依赖"记住端口号"这个前提**。`gen_images_*.sh` / `feishu_push` 调用前一律
   `unset HTTPS_PROXY HTTP_PROXY https_proxy http_proxy` + `export NO_PROXY="*"`,
   git push 一律 `-c http.proxy= -c https.proxy=`。这套做法对端口变化免疫。

### 3. db_save.py 日志文案是硬编码的, 会误导人读数
`db_save.py:172` 打印 `f"  ✅ product_competitors: {n_competitors} 项 (5 组 × 4 项)"`。
今天实际写入 **25 项(5 组 × 5 项)**, 但括号里硬编码写着 "4 项", 两者矛盾。
差点让人误以为漏写了一个竞品而去"补"数据。
→ **教训: 日志里的固定文案不能当校验依据, 一律以 `validate_schema.py` 的数字为准**
   (本次 validate 输出 `product_competitors: 25`, 正确)。
   ⚠️ 待办: 建议把 `db_save.py:172` 改成从实际分组数动态计算, 否则每天都会误导。

### 4. prompt.md 里 history.json 的内联脚本是坏的(老坑, 今天直接绕开)
prompt.md step 13 的内联 `python3 -c "..."` 片段里混进了一行孤立的 `202`
(应为 `2026-10-20` 的残留), 直接复制会 SyntaxError。

### 6. cron prompt step 13 的 `git add` pathspec 是错的(会让整批提交静默失败)
prompt 里写的是 `git add output/${TODAY}/ history/ history.json data.json vs-data.json v/ index.html`,
但 `history.json` 实际在 `history/` 目录下, 根目录没有这个文件 →
`fatal: pathspec 'history.json' did not match any files`。
更坑的是 **git add 遇到坏 pathspec 会整批中止**, 已经 `add` 成功的路径也一起作废,
后面紧接着的 `git commit` 报 "no changes added to commit", `git push` 报 "Everything up-to-date"——
**整条链路看起来都"成功"了, 实际一个文件都没推上去**。
→ **修复**: 改成 `history/`(目录形式已包含 history.json), 不再单独列 history.json。
   ⚠️ 判据: **别信 push 的 exit code, 要看 push 的输出有没有出现 `main -> main` 或 SHA 区间的行**。

### 7. GitHub Pages 推送后有约 40s 构建传播延迟, 别急着判定失败
push 成功后立刻 curl 线上, 拿到的是旧的 `DATA_VERSION` + 新 `v/{VERSION}/` 404,
看起来像"版本化路径没生效 / index.html 没更新"。
实测: push 后 20s 仍旧, **40s 后 DATA_VERSION 与 v/{VERSION}/data.json 同时变为正确值**。
→ **教训: 遇到 404/旧值先轮询 2-3 分钟再下结论**, 不要立刻回滚或重复 push
   (重复 push 只会多造一个空版本目录)。
