# Bug Fix: 8/21 推送后页面一直显示历史数据

## 症状
2026-08-21 11:36 用户反馈："为什么一直显示历史数据 不会动态更新了"

## 根因
index.html 第 6-8 行的 meta cache-control 写错了:
```html
<meta http-equiv="Cache-Control" content="1787267344" />  <!-- ❌ -->
```
把 DATA_VERSION 当成了 meta 的 content 值。但 `http-equiv="Cache-Control"` 的 content 必须是合法 HTTP 缓存指令(例如 `no-cache, no-store, must-revalidate`),版本号不是合法指令 → **浏览器直接忽略整行 meta**。

## 链路
1. 8/20 第一次 push 时,index.html 被浏览器缓存 10 分钟(max-age=600)
2. 8/21 7:10 push 后,index.html 的 ETag 变了,但用户浏览器里**还是 8/20 的旧 HTML**
3. 旧 HTML 里的 `const DATA_VERSION = '1787180867'` → fetch `./v/1787180867/data.json` → 旧版本路径在 8/21 不存在(被新 commit 覆盖) → 404
4. fallback 到 `./data.json?v=...` → 也命中 10 分钟 CDN 缓存 → 显示 8/20 数据

## 修复
commit `2216e1e`:
```html
<meta http-equiv="Cache-Control" content="no-cache, no-store, must-revalidate" />
<meta http-equiv="Pragma" content="no-cache" />
<meta http-equiv="Expires" content="0" />
```

新 ETag: `6a878986-c255` (旧 `6a878986-19e7`)

## 用户操作
**Cmd+Shift+R 强刷一次** 拿到新 HTML,以后浏览器就不再缓存这个 HTML。

## 教训(cron prompt 优化方向)
- `http-equiv` meta 的 content 必须是合法 HTTP 头值,不能塞版本号
- cron prompt step 12 里的 `sed -i '' "s/content=\"[^\"]*\" \/>/content=\"${VERSION}\" \/>/"` 会**误伤**所有 meta 的 content 属性(不只是 cache-control),改成只 sed 替换 `const DATA_VERSION` 就够了
- cron prompt 建议加一个 lint 检查: index.html 里的 meta cache-control content **不能等于** DATA_VERSION
