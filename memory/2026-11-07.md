### 🔥 本次 push 故障：**github.com:443 直连被卡**（本机无任何代理端口在监听）

3. DNS 正常：`github.com → 20.205.243.166`（GitHub 香港 IP）。
4. **对照组最关键**：直连 `smzdm.com` / `cloudimgs.iepose.cn` / `baidu.com` **全是 200**，

### 🛠 本次顺手修好 `push_with_probe.sh`（加第 3 层通道降级）

原脚本只有「代理 / 直连」两层，遇到今天这种「无代理 + 直连被卡」就必然失败（还会白等 75s）。
改成 **3 层逐级降级，每层都先 curl 探活再真 push**（避免 git 干等超时）：

1. **代理** —— 环境变量 + 常见端口，端口有监听**且**经它访问 github.com 返回 200
2. **直连** —— `curl --noproxy '*'` 访问 github.com 返回 200
3. **直连 + 指定可达 IP** —— 动态向 `1.1.1.1 / 8.8.8.8 / 223.5.5.5` 解析 github.com 的 A 记录
   + 一份常见 GitHub IP 兜底列表，逐个 `curl --resolve` 实测，用第一个返回 200 的
   → `git -c http.proxy= -c https.proxy= -c http.curloptResolve=github.com:443:<IP> push`

同时加了两处：

## 🐛 踩坑汇总
1. **github.com:443 可能整条被卡（今天真实遇到）**：本机**无任何代理端口在监听**（clash 只有特权 helper，内核没跑），
   直连 github.com 75s 超时，但 smzdm / cloudimgs / baidu 直连全 200 → **只有 GitHub 这条路被卡**。
   → **换 GitHub 的其它 A 记录即可**（`140.82.112.3` / `140.82.113.3` / `140.82.114.3` 实测 200），
   用 `git -c http.proxy= -c https.proxy= -c http.curloptResolve=github.com:443:<IP>`。
