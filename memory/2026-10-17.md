## 🐛 Bug 发现与修复 (今日新增, 明天务必注意)

### 1. ⚠️⚠️ 父 shell 注入死代理 7897 —— 昨天写的"直连"方案今天不够用了

10/16 的修复结论是「proxy 7897 已下线, 直连 api.minimaxi.com 正常」,
所以今天第一版 `gen_images_20261017.sh` **完全没设任何代理**, 直接调 mmx。
结果 5 张图全部失败:

```json
{"error": {"code": 6, "message": "Network request failed."}}
```

排查:
```bash
env | grep -i proxy
# HTTP_PROXY=http://127.0.0.1:7897
# HTTPS_PROXY=http://127.0.0.1:7897   ← 父 shell 早就 export 了
lsof -nP -iTCP -sTCP:LISTEN | grep 7897   # 依然无进程监听
```

**根因**: 我以为"脚本里不写代理 = 直连", 但 mmx 是子进程, **继承父 shell 的
HTTP(S)_PROXY 环境变量**。7897 无监听 → 所有请求瞬间失败。
昨天之所以"直连能通", 是因为昨天那次是在一个没有 export 代理变量的会话里跑的。

**修正**(已写入 `scripts/gen_images_20261017.sh` 顶部):
```bash
unset HTTPS_PROXY HTTP_PROXY https_proxy http_proxy
export NO_PROXY="*"
export no_proxy="*"
```
补 `NO_PROXY="*"` 是双保险 —— 某些 SDK 读的是小写变量或 NO_PROXY。
改完 5 张图全部一次成功。

> ⚠️ 明天起: **任何调 mmx / cloudimgs / GitHub 的脚本, 开头都要先 unset 这几个变量**,
> 不要依赖"我不写代理变量就会直连"这个错误假设。

### 2. ⚠️ validate_schema.py 硬编码 `n_comp != 20`, 今天多写了 5 条真实竞品被判失败

今天按搜索深度给每组写了 5 条竞品(共 25 条), 结果:
```
❌ product_competitors 应 20, db 里 25
```

**根因**: `scripts/validate_schema.py` 第 61 行从 9/2 起就写死
`if n_comp != 20:  # 5 组 × 4 项` —— 这个 20 只是 9/2 那天恰好每组 4 条的快照,
不是数据完整性约束。竞品条目随当天搜索深度浮动本来就正常。

**修正**: 改成「每组至少 4 条」的真实完整性校验:
```python
MIN_PER_GROUP = 4
# LEFT JOIN + GROUP BY p.product_id, 逐组检查
for pid, n in comp_groups:
    if n < MIN_PER_GROUP:
        errors.append(f"❌ product {pid} 竞品仅 {n} 项, 至少需 {MIN_PER_GROUP} 项")
```
这样**整组缺失照样报错**(比原来的总数校验更精准), 但不再惩罚更丰富的选品日。

### 3. ⚠️⚠️ `git push` 走不通 —— github.com 的 HTTPS 在本机被墙, 改走 Git Data API

`git -c http.proxy= -c https.proxy= push origin main` 报:
```
fatal: unable to access 'https://github.com/where20/xhs-product-push.git/':
       Recv failure: Operation timed out
```
排查结果 —— **不是代理问题, 是 github.com 这个 host 本身不可达**:

| 目标 | 直连 (--noproxy '*') | 结论 |
|------|------|------|
| `github.com` (git/https) | 超时 20s 无响应 | ❌ 不可达 |
| `api.github.com` | 200, 0.34s | ✅ 通 |
| `codeload.github.com` | 301, 0.91s | ✅ 通 |
| `raw.githubusercontent.com` | 301, 0.59s | ✅ 通 |
| `objects.githubusercontent.com` | 404, 0.24s | ✅ 通(404=服务正常) |
| SSH `git@github.com:22` | 握手成功 | ⚠️ TCP 通但 `Permission denied (publickey)` |

- 本机代理 7897 依然无进程监听; 扫了 1080/1087/2080/7890/8888/10809 等 15 个常见端口,
  只有 `2080`(nlink 的 VPNPacket)在监听 —— 实测既不是 HTTP 代理也不是 SOCKS5, 不可用。
  Clash Verge 服务装了但主程序没跑。
- SSH 走不通的原因: 本机 `~/.ssh/id_rsa.pub` 没在 GitHub 注册,
  而 keychain 里的 token (`gho_...`, 属于 `where20`) **缺 `admin:public_key` scope**,
  `POST /user/keys` 直接返回 404 Not Found, 无法自动注册公钥。

**修正**: 既然 `api.github.com` 通, 就不走 git 协议, 直接用 **Git Data API** 建 commit:
```
POST /git/blobs   (每个文件一个 blob)
POST /git/trees    (base_tree = 远端 HEAD 的 tree, 叠加当天 28 个文件)
POST /git/commits  (parents = 远端 HEAD)
PATCH /git/refs/heads/main
```
结果: `main` 远端 → `f65dc23`, 28 个文件全部落地, GitHub Pages 约 30s 内完成部署,
线上 `https://xhs.220616.xyz/v/1792191986/data.json` 已确认返回今天的 5 个商品。

脚本: `scripts/push_via_api.py <YYYY-MM-DD> [VERSION]`(VERSION 省略时读 `.last_version`)。
它**基于远端 HEAD 叠加当天文件**, 因此完全不看本地 git 状态, 天生幂等 ——
明天即使本地有未推送的 commit 也不影响。

踩坑细节: 大图 base64 后有 3MB+, 用 `curl -d "$json"` 传会撞
`OSError: [Errno 7] Argument list too long`。已改成写临时文件 + `-d @file`。

> ⚠️ 本地 `git push` 与远端已分叉: 本地 HEAD `58ec27d`(内容与远端 `f65dc23` **完全一致**,
> 891 个 blob 逐一比对无差异; tree SHA 不同是因为 `xhs-ai-pack/` 下 3 个中文文件名
> 的 Unicode 规范化形式差异, 不影响内容)。**明天起不要再用 `git push`, 一律走 push_via_api.py。**
